# 加速方案：气候模拟专用（MacBook Pro 2024 / Apple Silicon）

## 一、目标平台硬件分析

MacBook Pro 2024 搭载 Apple M4 系列芯片，统一内存架构。M4 基础版内存带宽 120 GB/s，M4 Pro 约 273 GB/s，M4 Max 达到 **546 GB/s**，最高 128 GB 统一内存，GPU 最高 40 核，FP16 算力约 54 TFLOPS。统一内存架构意味着 CPU 和 GPU **共享同一物理内存**，数据在设备间传输无需拷贝，这对气候模拟中的大数组操作是天然优势。

关键限制：**Apple GPU 不原生支持 Float64**。M4 和 M5 GPU 的 MPS 后端不支持 float64 数据类型。这意味着所有 GPU 加速路径必须使用 **Float32**。对于气候模拟，Float32 的精度完全足够（温度场保留约 7 位有效数字，在 -100°C 到 +100°C 范围内精度约 0.0001°C），但在求解椭圆方程和长时间积分时需要特别注意数值漂移的累积。

**加速技术可用性**：

| 技术 | Mac 支持状态 | 适用模块 |
|------|-------------|---------|
| NumPy 向量化 | 原生支持 | 所有模块 |
| Numba JIT（CPU） | 原生支持，M 系列优化良好 | 地形、侵蚀、降水参数化 |
| Taichi（Metal GPU） | 支持，需 Python 3.13 | 地形、侵蚀 |
| MLX（Metal GPU） | Apple 原生框架，最佳 GPU 支持 | 大气动力学、海洋、辐射 |
| JAX + jax-metal | 实验性，稳定性一般 | 备选（生态丰富） |
| JAX + MLX Plugin | 社区插件，支持核心算子 | 备选 |
| PyTorch MPS | 支持，float64 受限 | 代理模型训练 |
| ExoPlaSim | 原生支持 Mac（需 Xcode + gfortran） | 中间复杂度 GCM 验证 |


## 二、框架选型：MLX vs JAX 在 Apple Silicon 上的权衡

在 Apple Silicon 上，GPU 加速的核心选择是 **MLX** 还是 **JAX**。

**MLX** 是 Apple 为 Apple Silicon 专门设计的数组框架，直接编译到 Metal。在**通用数值计算**（如 stencil 运算、FFT、矩阵求解）方面，MLX 比 JAX-Metal 略快。MLX 的 API 风格接近 NumPy，学习曲线低，且对 Metal 的支持最成熟、更新最及时。对于气候模拟中的规则网格计算（梯度、散度、旋度、时间积分），MLX 是首选。

**JAX** 拥有更丰富的生态系统（`lax.scan`、`vmap`、自动微分），但 **jax-metal 的稳定性一直不佳**。Apple 官方的 jax-metal 插件存在 JIT 相关问题，有开发者报告“截至 2026 年初仍然不稳定”，并已完全转向 MLX。社区开发的 **jax-mlx-plugin** 让 JAX 通过 MLX 运行在 Metal 上，支持核心算子、自动微分、`lax.scan`、FFT 和线性代数，但 Float64 在 Metal 上不原生支持，且 `while` 循环会阻塞内核融合。**iree-metal** 是另一个实验性 JAX 后端，仅支持 Apple M4 + CPython 3.12 + JAX 0.6.1 的特定组合。

**推荐策略**：

- **核心求解器**（大气动力学、海洋环流、辐射传输）：用 **MLX**。直接利用 Metal GPU，规避 JAX-Metal 的稳定性问题。
- **地形生成和侵蚀模拟**：用 **Numba（CPU）** + **Taichi（GPU，可选）** 。Numba 在 M4 Pro 上实现 56× 加速，Taichi 实现 78× 加速。
- **参数优化和自动微分**：如果 MLX 的自动微分满足需求则用 MLX；否则用 **JAX + jax-mlx-plugin** 作为备选。
- **中间复杂度 GCM 验证**：用 **ExoPlaSim** 作为物理基准和参考实现。ExoPlaSim 支持 Mac OS X，需要 Xcode 和 gfortran 编译器。


## 三、各气候模块的加速方案

### 3.1 行星辐射强迫

辐射强迫的计算热点是**逐网格、逐时间步的三角函数批量计算**。在 MLX 中，将所有纬度和时间步的三角函数一次性计算：

```python
import mlx.core as mx

def daily_insolation(phi, delta, S0, a_over_r_sq):
    # phi: (nlat, 1, 1), delta: (1, 1, ntime)
    cos_H0 = mx.clip(-mx.tan(phi) * mx.tan(delta), -1.0, 1.0)
    H0 = mx.arccos(cos_H0)
    return (S0 / mx.pi) * a_over_r_sq * (
        H0 * mx.sin(phi) * mx.sin(delta) +
        mx.cos(phi) * mx.cos(delta) * mx.sin(H0)
    )
```

在 M4 Max 的 GPU 上，全球 1° 分辨率（65,000 网格点）× 365 天的辐射场计算预期在**毫秒级**完成。辐射场只依赖行星参数，可以**预计算并缓存为 Zarr 文件**，后续气候模拟直接读取。

### 3.3 地表能量平衡

地表能量平衡的隐式温度求解可以完全向量化。MLX 支持 `mx.where`、`mx.clip` 等条件操作，适合处理不同地表类型（海洋/陆地/冰）的参数差异：

```python
def solve_surface_temperature(Ts, Ta, qa, u, Rnet, params):
    # 饱和比湿及其导数
    qs = saturation_specific_humidity(Ts, params.p_surf)
    dqs_dT = params.L * qs / (params.Rv * Ts**2)
    
    # 稳定度修正
    Ri_B = params.g * params.z_a * (Ta - Ts) / (Ta * u**2 + 1e-6)
    C_H = params.C_H0 * stability_factor(Ri_B)
    
    # 隐式求解
    numerator = (params.C_s * Ts / params.dt + Rnet + 
                 params.rho * params.cp * C_H * u * Ta +
                 params.rho * params.L * C_E * u * (qa - qs + dqs_dT * Ts))
    denominator = (params.C_s / params.dt + 
                   4 * params.eps_s * params.sigma * Ts**3 +
                   params.rho * params.cp * C_H * u +
                   params.rho * params.L * C_E * u * dqs_dT)
    
    Ts_new = numerator / denominator
    H = params.rho * params.cp * C_H * u * (Ts_new - Ta)
    LE = params.rho * params.L * C_E * u * (qs_new - qa)
    return Ts_new, H, LE
```

对于土壤热传导的多层时间积分，用 **Numba** 在 CPU 上并行处理（M4 Max 的 16 核 CPU 在此类 stencil 计算上效率很高），或者用 MLX 在 GPU 上做批量并行。

### 3.4 大气动力学

大气动力学是**计算量最大的模块**（占总计算时间的 40–60%），涉及时间积分循环和谱变换。

**方案 A：MLX 实现浅水/原始方程**（推荐）

用 MLX 的 `mx.roll` 实现球面 stencil 计算（梯度、散度、旋度），用 Python 循环做时间积分（MLX 的 JIT 编译会融合操作）：

```python
import mlx.core as mx
import mlx.nn as nn

@mx.compile
def shallow_water_step(u, v, h, params):
    # 球面 stencil（使用 mx.roll 实现周期边界）
    du = -u * grad_lon(h) + params.f * v
    dv = -v * grad_lat(h) - params.f * u
    dh = -div(u * h, v * h)
    return u + du * params.dt, v + dv * params.dt, h + dh * params.dt

def integrate(state, n_steps):
    for _ in range(n_steps):
        state = shallow_water_step(*state, params)
    return state
```

MLX 的 `@mx.compile` 会将整个函数体编译为融合的 Metal kernel，消除中间数组分配。对于年尺度积分（约 10,000–100,000 时间步），这比 NumPy 快 50–100×。

**方案 B：ExoPlaSim 作为动力学核心**（推荐用于物理验证）

ExoPlaSim 是基于 PlaSim 的中间复杂度 GCM，T21 分辨率（约 5.6°）、10 层，一年气候积分在 **1 分钟以内**完成。它支持 Mac OS X，有 Python API，可以通过 `ncpus` 参数指定并行核心数。对于虚拟行星生成器，可以将 ExoPlaSim 作为**物理基准**，用 MLX 实现快速版本，两者的输出做交叉验证。

### 3.5 海洋环流

海洋环流的时间积分可以用与大气动力学相同的 MLX 策略。风应力旋度和 Ekman 抽吸的计算是逐网格操作，适合 GPU 并行。

**热盐环流的 Stommel 两箱模型**只有 2 个变量，计算量极小，用纯 Python 即可，不需要 GPU 加速。

**三维海洋环流**（Boussinesq 方程）的计算量最大，如果启用，需要用 MLX + 域分解（将纬度带分给不同 GPU kernel 并行处理）。

### 3.6 降水参数化

降水参数化的计算热点是 CAPE 的垂直积分。在 MLX 中完全向量化：

```python
def compute_cape(T, q, p, z):
    Tv = T * (1 + 0.61 * q)
    T_parcel = T[0] - 0.0098 * (z - z[0])
    buoyancy = 9.81 * (T_parcel - Tv) / Tv
    cape = mx.trapz(mx.maximum(buoyancy, 0), z, axis=0)
    return cape
```

地形降水和再蒸发也是逐网格操作，适合 GPU 批量并行。

### 3.7 Köppen 气候分类

Köppen 分类不涉及时间积分，计算量最小。在 1° 分辨率下，用 **NumPy 向量化**即可（毫秒级）。只有在高分辨率（> 10⁷ 网格点）下才需要考虑 GPU 加速。MLX 的 `mx.where` 嵌套可以替代 `np.where` 嵌套，在 GPU 上批量执行。


## 四、统一的内存与数据布局策略

在 Apple Silicon 的统一内存架构下，**避免 CPU-GPU 之间的数据拷贝**是加速的关键。MLX 数组与 NumPy 数组之间的转换有开销，因此建议：

**全局使用 MLX 数组**：从地形生成到气候模拟到可视化，尽可能保持数据在 MLX 数组中。仅在需要保存到磁盘（Zarr/NetCDF）或与外部库（Matplotlib、PyVista）交互时，才转换到 NumPy。

**数据布局**：对于立方球网格，将所有 6 个面的数据打包为 `(6, nlat, nlon)` 的连续数组，face 索引在最外层。这使 MLX 的 `mx.roll` 和 stencil 操作可以高效执行。

**精度策略**：GPU 路径统一使用 **Float32**。仅在 CPU 上的长时间积分（如 1000 年以上的 Spin-Up）中使用 Float64，以控制数值漂移。MLX 在 M4 GPU 上的 Float32 吞吐量远高于 CPU 上的 Float64。


## 五、多世界并行策略

虚拟世界生成器通常需要**同时生成多个不同种子的世界**。在 MacBook Pro 上，可以利用 M4 Max 的 16 核 CPU 做多进程并行：

```python
from joblib import Parallel, delayed

results = Parallel(n_jobs=12)(
    delayed(generate_world)(seed, params) for seed in seeds
)
```

每个进程负责一个世界的完整生成管线（地形 → 气候 → 分类）。由于 MLX 在 GPU 上的计算是串行的（一个 GPU 同一时刻只能执行一个 kernel），多进程并行主要利用 CPU 核。对于需要 GPU 加速的单个世界，**串行生成多个世界**，每个世界用 GPU 加速内部计算。


## 六、缓存与 IO 策略

气候模拟的数据量很大。以 1° 分辨率、10 个变量、2 个季节为例，单次快照约 **520 MB**（Float32）。推荐使用 **Zarr** 分块存储：

```python
import zarr

# 创建分块存储
store = zarr.open('world_output.zarr', mode='w')
store.create_dataset('temperature_jan', 
                     shape=(nlat, nlon), 
                     chunks=(180, 360), 
                     dtype='float32')
```

**缓存策略**：
- **地形数据**：一旦生成，缓存为 Zarr，后续气候模拟直接读取。
- **辐射场**：预计算整年的日平均辐射场，缓存为 Zarr。
- **中间气候结果**：月温度和月降水缓存，Köppen 分类调整时不需要重新计算气候场。

## 九、实践建议

**先跑通再优化**。用 ExoPlaSim 在 T21 分辨率（约 5.6°）上跑通完整的行星参数 → 气候场 → Köppen 分类管线，验证物理正确性。然后用 MLX 重写核心求解器，逐步提高分辨率。

**Profiling 优先**。用 `cProfile` 和 MLX 的性能分析工具找热点。通常 90% 的时间在少数几个 kernel 中。先优化这些 kernel，不要盲目重写全部代码。

**Float32 是默认精度**。GPU 路径统一使用 Float32。只在 CPU 上的长时间 Spin-Up 中使用 Float64。

**缓存一切可以缓存的**。地形、辐射场、月气候统计量都是静态的，用 Zarr 缓存，避免重复计算。

**备份路径**：如果 MLX 的某个算子不支持或性能不佳，退回到 Numba CPU 版本。Numba 在 M4 Pro 上的单线程性能相当于 M1 的多核性能，足以作为备选方案。
